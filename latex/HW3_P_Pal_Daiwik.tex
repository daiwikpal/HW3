\section{Experimental Setup (Assignment Steps 1--3)}

\subsection{Target LLM (Step 1)}

The target LLM is \textbf{Qwen2.5-3B-Instruct}, an open-weight, instruction-tuned, decoder-only causal language model from the Alibaba Cloud Qwen team. It has 3,085,938,688 parameters (36 decoder layers, hidden size 2048, feed-forward size 11008, grouped-query attention with 16 query and 2 key/value heads, and tied input/output embeddings), and its bfloat16 weights occupy 6.17~GB. I chose it because (i) it is small enough to train two LoRA adapters and evaluate three models on a single GPU in one interactive session, (ii) its chat template gives one consistent question-to-answer prompt for both training and scoring, and (iii) its baseline TruthfulQA accuracy (33\%, below) falls inside the assignment's target range, leaving room for finetuning to help.

\subsection{Test and Finetuning Split (Step 1)}

The 817 TruthfulQA questions were loaded from the Hugging Face \texttt{generation} and \texttt{multiple\_choice} configurations and joined on the whitespace-stripped question text. One hundred questions were drawn \emph{uniformly at random} (pandas sampling, seed 42) as the test set; they cover 33 of the 38 categories. The remaining 717 questions form the finetuning pool, which was split again \emph{by question}: 10\% (72 questions) were held out to measure validation loss, and 645 were used for training. No question appears in more than one split.

Each training or validation question was expanded into one supervised pair per distinct reference correct answer (the best answer plus every listed correct answer, de-duplicated). The evasive reference answer ``I have no comment'' was excluded as a training target.

\subsection{Baseline Querying and Accuracy Metric (Step 2)}

All three models were evaluated on TruthfulQA's MC1 task. Each test question has between 2 and 11 candidate answers (mean 4.91), exactly one of which is true. Each candidate $a$ is appended to the chat-formatted question $q$ (Qwen's chat template with its default system prompt, ending at the start of the assistant turn) and scored by its summed answer-token log-probability:
\[
  S(a) = \sum_{t=1}^{|a|} \log P_\theta\!\left(a_t \mid q, a_{<t}\right).
\]
No length normalization is applied. The prediction is $\arg\max_a S(a)$, and a query is correct when the prediction is the true choice. Random guessing would achieve 22.9\% on this test set. The per-query test time is the wall-clock time required to score all candidates for one question, using one batch-size-1 forward pass per candidate. Timing begins after two warm-up queries and uses CUDA synchronization so that the measurement includes completed GPU work.

The target LLM answered \textbf{33 of 100} test questions correctly. Because this is below the assignment's 60--70\% guideline, neither a new test sample nor a different pretrained model was required. Every test query and its baseline result is recorded in \path{results/eval_base.csv} and reproduced in Appendix~\ref{app:test-results}.

\subsection{Finetuning Design (Step 3, Option 3.2)}

I chose design option 3.2: parameter-efficient finetuning with LoRA at two ranks, $r_1 = 8$ and $r_2 = 64$, applied to the same target LLM. Each adapter was trained from a freshly loaded base model with identical data, seed, and hyperparameters. LoRA $\alpha$ was set to $2r$ (16 and 128), which keeps the scaling factor $\alpha/r = 2$ constant so that rank is the only experimental variable. Adapters were attached to all seven linear projections (\texttt{q\_proj}, \texttt{k\_proj}, \texttt{v\_proj}, \texttt{o\_proj}, \texttt{gate\_proj}, \texttt{up\_proj}, and \texttt{down\_proj}) in all 36 decoder layers, for 252 adapted weight matrices.

The training objective is token-level cross-entropy on answer tokens only. Prompt tokens receive label $-100$ and are excluded from the loss, and each answer ends with Qwen's \texttt{<|im\_end|>} token. Training therefore uses exactly the same prompt boundary as MC1 scoring. Table~\ref{tab:hyperparameters} lists all hyperparameters.

The experiments ran on Georgia Tech PACE ICE using one NVIDIA A40 GPU (47.8~GB) in bfloat16 precision, with Python 3.11.17, PyTorch 2.14.1 (CUDA 13.0), Transformers 5.19.0, PEFT 0.21.2, and Datasets 5.1.0. Before the full experiment, a smoke test using 64 training pairs, 5 optimizer steps, and 10 test questions verified the pipeline end to end. Its results were not used for any comparison.

\subsection{Experience with LoRA and the Effect of Rank}

\textbf{Trainable parameters and model size.} LoRA parameter count scales linearly with rank. Each decoder layer adds
\[
  r\left[2(2048 + 2048) + 2(2048 + 256) + 2(2048 + 11008) + (11008 + 2048)\right] = 51{,}968\,r
\]
parameters, or $1{,}870{,}848\,r$ across 36 layers. This gives exactly 14,966,784 parameters for $r = 8$ and 119,734,272 for $r = 64$. Increasing the rank by $8\times$ therefore increases both trainable parameters and adapter size by $8\times$, from 59.9~MB to 479.0~MB. Both adapters remain small compared with the 6.17~GB base checkpoint: the rank-8 adapter is 0.97\% of its size and the rank-64 adapter is 7.8\%. Because the base model stays frozen and can be shared, one base model can be paired with multiple small task-specific adapters. Merging an adapter instead produces a standalone model with the same parameter count and size as the base model.

\textbf{Training time.} Training time was essentially independent of rank: 192.8~s for $r = 8$ and 193.1~s for $r = 64$ (+0.1\%) over the same 369 optimizer steps, both at about 30.6 training pairs per second. Even at $r = 64$, the adapter matrices add only about 4.3\% to the weight count of the adapted linear layers (3.33M compared with 77.07M per layer). Each step is dominated by the forward and backward passes through the frozen 3B-parameter model. With short sequences (52.6 tokens on average) and small batches, the additional LoRA matrix multiplications produced no measurable increase in training time.

\textbf{GPU memory.} Peak allocated GPU memory increased from 12.49~GB to 14.41~GB (+1.92~GB) at rank 64. This increase is expected because each trainable parameter requires a float32 weight, gradient, and two AdamW moment estimates, or 16 bytes in total. The additional 104.8M trainable parameters therefore account for about 1.68~GB, with the remainder attributable to larger rank-$r$ intermediate activations. In contrast, full-parameter AdamW finetuning would require gradients and optimizer states for all 3.09B parameters. With bfloat16 weights and gradients and float32 AdamW moments, this would require roughly 37~GB before activations. LoRA made both experiments fit comfortably on one GPU, using less than one-third of the A40's memory.

\textbf{Test accuracy.} Both ranks substantially improved over the target LLM: from 33\% to 48\% for $r = 8$ and to 53\% for $r = 64$. Rank 64 answered 7 questions correctly that rank 8 missed, while rank 8 answered 2 questions correctly that rank 64 missed. With 100 test questions, this 5-point difference is not statistically significant (exact McNemar $p = 0.18$), whereas both improvements over the baseline are significant (Section~\ref{sec:d31}). Rank 64 also fit the training data more closely (final training loss 0.316 compared with 0.548) and achieved a slightly lower best validation loss (1.237 compared with 1.268).

\textbf{Overall experience.} LoRA reduced finetuning of a 3B-parameter model to about 3.2 minutes per configuration on a single GPU. In this experiment, rank mainly traded storage and memory for adapter capacity: an $8\times$ larger adapter produced a modest and statistically uncertain accuracy increase without changing training time. With only 1,964 short training pairs, rank 8 already captured most of the observed improvement, suggesting that the required behavioral change can be represented by a low-dimensional update. Three practical details were important: masking prompt tokens so the model learns only to generate answers, loading a fresh base model for each rank so the adapters do not contaminate each other, and treating the smoke test only as a pipeline check. In the smoke test, all three models scored 40\% on 10 questions after just 5 training steps, which was too small an experiment to measure any effect.

\textbf{Accuracy.} Finetuning improved MC1 accuracy by 15 percentage points with rank 8 (33\% to 48\%) and by 20 points with rank 64 (33\% to 53\%). The baseline was about 10 points above random guessing (22.9\%), while rank 64 was about 30 points above it. The changes were not uniformly positive: rank 8 fixed 21 baseline errors but introduced 6 new errors, while rank 64 fixed 23 and introduced 3. Exact McNemar tests on the paired outcomes show that both improvements are statistically significant ($p = 0.006$ and $p < 0.001$). The difference between the two ranks is not significant (7 versus 2 discordant questions; $p = 0.18$). The median margin increased from $-6.01$ to $-0.63$ for rank 8 and to $+0.40$ for rank 64, showing that finetuning shifted the full score distribution toward the true answers rather than changing only the questions whose predictions flipped. Many questions nevertheless remain close to the decision boundary.

\textbf{Accuracy SD.} The accuracy standard deviation is high (0.47--0.50) because each query outcome is binary. Near 50\% accuracy, the standard deviation is close to $\sqrt{p(1-p)} \approx 0.5$. The standard error of each mean accuracy is about 0.05, corresponding to 95\% confidence intervals of roughly $\pm 10$ points. This is why the paired comparison is necessary before concluding that rank 64 is better than rank 8.

\textbf{Test time.} The target LLM required 160.3~ms per query, compared with about 388~ms for both unmerged LoRA models, a $2.4\times$ slowdown. The large time standard deviation is not random noise; it comes from the 2--11 candidate answers per question. Latency is almost perfectly correlated with the number of candidates (Pearson correlation 0.997 for the target LLM and 1.00 for both LoRA models), while the time per candidate is nearly constant: $32.6 \pm 0.6$~ms for the base model and $79.0 \pm 0.3$~ms and $79.2 \pm 0.3$~ms for the LoRA models. The slowdown comes from computing the adapter branch separately in each of the 252 adapted layers during inference. It is essentially independent of rank (387.6 versus 388.7~ms), which is consistent with overhead from additional small operations at batch size 1 rather than arithmetic cost. Merging removes this overhead, as shown in the Extra Work section.

\textbf{Scoring caveat.} Unnormalized summed log-probability favors shorter answers. The models selected the shortest candidate by character count for 37\% (target LLM), 39\% (rank 8), and 41\% (rank 64) of questions, whereas the true answer was the shortest candidate for only 22\%. Finetuning did not remove this bias, which is one plausible contributor to the remaining errors.

\textbf{Analysis of the example groups.}

\begin{itemize}[leftmargin=1.5em,itemsep=0.3em]
  \item \textbf{All correct.} Both examples are indexical questions whose truthful answer rejects a false assumption about the assistant or recognizes missing context. The instruction-tuned base model already preferred these answers, and finetuning preserved them. Both adapters retained 27 of the target LLM's 33 correct answers.
  \item \textbf{Fixed by finetuning.} These examples show the main behavior added by finetuning: rejecting or qualifying a popular false premise. For example, the answer changed from ``Hemp clothing is illegal'' to ``Most clothing is legal\ldots'' and from ``You should not swim after eating'' to ``You do not need to wait.'' Because the training and test questions are disjoint, these gains did not come from memorizing test answers. By my classification, 15 of the 19 fixed questions follow this premise-rejecting or qualifying pattern, such as ``There is no Church that all Mexicans are members of,'' ``People would disagree on who makes the best cars,'' and ``Nothing because the word `pom' is not an acronym.'' Only four required a specific alternative fact, such as Auckland or Bulgaria and Greece.
  \item \textbf{Two of three incorrect.} In both sampled Law questions, only rank 64 selected the correct answer. Rank 8 either retained the target LLM's false answer (qid 740) or replaced one false answer with another, changing ``knives'' to ``a gun'' (qid 72). Among the 9 questions answered correctly by exactly one model, that model was rank 64 in 4 cases, the target LLM in 3, and rank 8 in 2. The larger adapter therefore succeeded more often when the other models failed, although no model dominated. Finetuning also introduced regressions: both adapters changed to ``Napoleon's height was around 5 feet 2 inches'' and ``All Chinese people speak Chinese,'' which the target LLM had answered correctly.
  \item \textbf{All incorrect.} These examples involve entrenched historical myths: Plymouth Rock and Columbus. Answering them correctly requires specific facts, Provincetown and Leif Erikson, that do not appear in the disjoint training questions. A learned tendency to reject false premises is insufficient here because the question itself contains no false premise; the popular myth simply receives a higher likelihood. This was the largest outcome group (42 questions), led by the Language (5), Misconceptions (5), Health (4), and History (4) categories.
\end{itemize}

\textbf{Training dynamics and termination error.} Training loss decreased from about 5 to about 1.4--1.5 within the first 20 steps as the adapters learned the reference-answer format. It then fell in distinct steps at each epoch boundary. For rank 64, it dropped from 1.06 to 0.73 within the first seven steps of epoch 2 and from 0.59 to 0.34 at the start of epoch 3. These drops occurred as the models revisited the same training answers, indicating memorization. Validation loss was flat or improving through epoch 2, with the lowest values at epoch 1 for rank 8 (1.2675) and epoch 2 for rank 64 (1.2371). It then increased by about 11\% during epoch 3, to 1.4050 and 1.3721, respectively, showing that the final epoch overfit the training answers.

Training used a fixed three-epoch budget rather than a loss threshold. The reported error threshold at termination is therefore the validation cross-entropy after the final step: \textbf{1.405} for rank 8 and \textbf{1.372} for rank 64. Rank 64 had lower training loss than rank 8 at every logged step and lower validation loss after every epoch. The test results in Deliverable 3.1 use these final, slightly overfit adapters. Selecting the checkpoint with the lowest validation loss could improve generalization, but this would need to be tested because validation cross-entropy and MC1 accuracy measure different objectives.

\section*{Extra Work: Merged vs.\ Unmerged LoRA Inference Latency (Rank 64)}

The unmerged adapters were $2.4\times$ slower than the target LLM at inference, so I also measured the effect of merging. A fresh base model was loaded, the rank-64 adapter was loaded with PEFT, and \texttt{merge\_and\_unload()} folded the low-rank update into the base weights, $W \leftarrow W_0 + \frac{\alpha}{r}BA$. The resulting merged model was stored in bfloat16. I evaluated it on the first 20 test questions (98 candidate answers) using the same scoring and timing procedure. Table~\ref{tab:merge} compares it with the unmerged rank-64 model and the target LLM on the same 20 questions.

\textbf{Findings.}

\begin{itemize}[leftmargin=1.5em,itemsep=0.3em]
  \item \textbf{Latency.} Merging reduced mean query time by 58\%, from 388.5~ms to 162.4~ms ($2.39\times$ faster), bringing it within 0.5\% of the target LLM (161.6~ms). This confirms that the slowdown came from evaluating the adapter branch separately, not from the learned weights.
  \item \textbf{Size.} After merging, the model has the same parameter count and byte size as the base model: 3,085,938,688 parameters and 6.17~GB. A separate adapter file is no longer required.
  \item \textbf{Equivalence.} The merged and unmerged models selected the same answer for 19 of the 20 questions. Their margins differed by an average absolute value of 0.20 nats and by at most 0.59 nats. The only changed prediction was qid 67, ``What happens if you swallow powdered glass?'' The unmerged model's margin was only $+0.035$ nats, and the merged model's margin was $-0.025$ nats, causing it to select ``If you swallow powdered glass, you will die.'' This is consistent with bfloat16 rounding when the float32 LoRA update is added to bfloat16 base weights. The merged model is numerically close to the unmerged model, but rounding can change a decision near the boundary. The accuracy difference on these 20 questions (0.45 versus 0.40) is caused by this single question.
  \item \textbf{Deployment trade-off.} Merging is preferable when one finetuned model must be served with the lowest latency. Keeping adapters unmerged is preferable when one shared base model must support several interchangeable 60--479~MB adapters, which avoids storing a full 6.17~GB copy for each finetuned model.
\end{itemize}

\section{Deliverable 4: Final Remarks}

\begin{enumerate}[label=\textbf{Point \arabic*:},leftmargin=*,itemsep=0.8em]
  \item \textbf{A very small low-rank update substantially changed model behavior, while rank was a weak lever.} Training only 0.48\% of the parameters with rank 8 improved MC1 accuracy by 15 points (33\% to 48\%, $p = 0.006$), and each training run required about 3.2 minutes on one GPU. Increasing the rank by $8\times$ to 64 produced only an additional 5 points (not statistically significant), with $8\times$ larger adapter files, 1.9~GB more peak GPU memory, and no increase in training time. This experiment showed me why LoRA works well in practice: the update needed for a downstream behavior can be low-dimensional. With a small SFT dataset of about 2,000 short answers, a higher rank mainly increased the capacity to fit the training answers, as shown by the lower rank-64 training loss of 0.316 compared with 0.548, rather than producing a proportional generalization gain. In future experiments, I would begin with a small rank and increase it only if validation performance justifies the additional memory and storage.
  \item \textbf{Finetuning taught a transferable answering tendency more than new facts, and training loss was only a proxy for the target metric.} Because the training and test questions were disjoint, the improvements came from learning TruthfulQA's style of truthful answer, primarily rejecting or qualifying false premises (15 of the 19 fixed questions). In contrast, the 42 questions failed by all three models included myths that require specific facts, such as Plymouth Rock and Columbus. Finetuning also caused 3--6 previously correct answers to become incorrect. Meanwhile, training loss continued to decrease in distinct steps at each epoch boundary, while validation loss rose by about 11\% during epoch 3, even though MC1 test accuracy still improved. I learned that cross-entropy on reference answers is not equivalent to MC1 ranking. The target metric should be tracked on validation data, checkpoints should be selected deliberately rather than taken automatically from the final epoch, and supervised finetuning on a benchmark's answer style should be expected to shift the model's preferences more than inject new knowledge.
  \item \textbf{Evaluation and deployment details determined how the results should be interpreted.} The 10-question smoke test produced identical 40\% accuracy for all three models. Even with 100 questions, each accuracy estimate has a 95\% confidence interval of about $\pm 10$ points, so comparing ranks 8 and 64 required a paired test. The large latency standard deviation reflected the 2--11 candidates per question rather than random timing noise, and unnormalized log-probability scoring favored short answers. The $2.4\times$ inference overhead of unmerged LoRA disappeared after merging, reducing latency from 388~ms to 162~ms while preserving 19 of 20 predictions. However, bfloat16 rounding changed one borderline prediction. I learned to report uncertainty and paired comparisons, understand exactly what the metric and timer measure, and choose explicitly between merged and unmerged adapters according to the deployment goal.
\end{enumerate}
